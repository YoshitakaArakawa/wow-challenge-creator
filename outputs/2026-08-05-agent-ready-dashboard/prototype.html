#WOW2026 W31: Can You Build an Agent-Ready Dashboard?

Draft · 20260805 · Difficulty: Beginner · Web Authoring only · Range 650–750 wide

Introduction

I have been running an experimental fork of the Tableau MCP server, trying to make dashboards live inside an AI chat. The piece I am most excited about is the viz state snapshot. You filter the embedded dashboard, the model gets told what you are now looking at, and it can go query the data source behind it. The dashboard stops being the end of the conversation and becomes something you and the agent are looking at together.

A dashboard built for that spot has to be small and it has to explain itself, because it turns up mid-conversation with nobody there to walk you through it. So this week, build one at close to a mobile size. On top of that, let's try Tableau Public's published data sources, which are new. Connecting to one is something you can only do in the browser, so this challenge is Web Authoring the whole way and Tableau Desktop stays closed. And since the chat app picks the width, the size below is a range rather than a fixed number.

Requirements

  • Set up
    • Dashboard size: Range, 650 x 800 minimum, 750 x 900 maximum
    • Build it entirely in Tableau Public Web Authoring, no Tableau Desktop
    • Connect to the published Sample Superstore 2026.2 data source, no file uploads
    • 5 sheets
  • Controls
    • Year Month, Region and Segment as single select dropdowns across the top
    • One parameter, Selected Measure, listing Sales / Profit / Profit Ratio and starting on Profit Ratio
  • The view
    • A KPI row showing Sales, Profit and Profit Ratio, measure name above the value
    • Bars of the selected measure by Sub-Category, sorted descending, colored so negatives read as negative
    • Bar values in a fixed width column to the right of the chart, right edges aligned on every row
  • Finishing touches
    • A light gray band behind the KPI row and behind the parameter control
    • Tooltips that stand alone: the sub-category, the name of the selected measure, and the value
    • Match the tooltips and formatting as closely as possible

Build spec (internal, not for the posted challenge)

Layout, top to bottom

  1. Title text — WOW2026 W31 at 15pt, then the question in Tableau Bold 20pt, ink #1b1b1b
  2. Blank 12px
  3. Filter band — horizontal container, background #f5f5f5, three dropdowns distributed evenly
  4. KPI row — horizontal container fixed at 80px high, three sheets distributed evenly, titles hidden
  5. Blank 12px
  6. Parameter band — horizontal container, background #f5f5f5, compact parameter control in the left third, two blanks filling the rest
  7. Chart row — KPI by SubCat scaling to fit (min 245) beside KPI by SubCat (Label) fixed at 92px
  8. Footer text — Data: Sample Superstore 2026.2, right aligned

Everything is tiled. No floating objects, which is what lets the range sizing actually stretch the chart between 650 and 750.

Fields

Selected Measure parameterinteger, list: 1 Sales, 2 Profit, 3 Profit Ratio. Default 3
Profit RatioSUM([Profit])/SUM([Sales]), formatted p0.0%
Selected Measure calcCASE on the parameter, returning SUM(Sales), SUM(Profit) or Profit Ratio
Label axisMIN(-1.0), axis fixed to max -1.0, title set to a single space

Sheets

Sales / Profit / Profit RatioOne text mark each. Custom label puts the measure name on line 1 at 12pt and the value on line 2 in Tableau Bold 15pt
KPI by SubCatRows Sub-Category, columns and color both Selected Measure, sorted descending. Row header 145px, font 12, field labels off. Default diverging palette, no saved override
KPI by SubCat (Label)Same rows, columns MIN(-1.0), text Selected Measure. Row header hidden, gridlines and zero line off

Three things to settle before posting

  1. The bar chart axis title is hardcoded to "Profit Ratio". Switch the parameter to Sales or Profit and the axis still says Profit Ratio. Either make it dynamic or drop the axis title entirely.
  2. The value column shows raw decimals (0.460) while the KPI row shows 7.5%. The same measure is formatted two different ways in the same view.
  3. The title has no "mobile" in it. That is consistent with the real subject being embed width rather than phones, but the requirements should carry the range sizing line prominently so the point lands.
